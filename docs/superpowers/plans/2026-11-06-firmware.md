# Firmware ZMK — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un firmware ZMK pour le NULL/PAD, compilé par GitHub Actions dans le dépôt `Telooss/NULL-PAD`. Il fait du pad un pavé numérique autonome (profil 1). Il donne 8 profils (couches ZMK) choisis par M1–M3, envoie au moteur les codes « action » et « annonce de profil » qu'il attend, affiche le tag du profil sur le nice!view et reste éditable par ZMK Studio.

**Architecture:** un shield ZMK `null_pad` (plus `nice_view_adapter` et `nice_view`) pour la carte `nice_nano_v2` (le SuperMini est un clone du nice!nano v2). Tout est dans `firmware/` du dépôt : `firmware/config/` (west.yml, keymap, conf, shield sous `boards/shields/null_pad/`) et `firmware/build.yaml`. Le workflow `.github/workflows/firmware.yml` appelle le workflow officiel `build-user-config.yml` de ZMK, épinglé sur `v0.3.0`. Les codes action sont calculés par une macro du préprocesseur, `ACT(profil, entrée)`, qui recopie la formule du moteur. Un test Rust du moteur vérifie que l'en-tête et `codes.rs` donnent les mêmes valeurs.

**Tech Stack:** ZMK **v0.3.0** (Zephyr 3.5, carte `nice_nano_v2`), devicetree / Kconfig, GitHub Actions, Rust (un test et un changement de config par défaut dans `engine`).

**Spec:** `docs/superpowers/specs/2026-11-05-logiciel-macropad-design.md` (§3.1 Firmware, §4 Profils). Matériel : `PROJECT.md` du dossier matériel (hors dépôt), sections « Pinout » et « Layout ». Codes : `docs/superpowers/plans/2026-11-05-moteur.md`, « Table des codes ».

## Faits vérifiés dans les sources de ZMK v0.3.0 (2026-11-06)

- **Version.** Dernière version publiée : `v0.3.0` (2025-08-01), sur Zephyr 3.5, où la carte s'appelle encore `nice_nano_v2`. La branche `main` est passée à Zephyr 4.1 et a d'autres noms de cartes : on reste sur `v0.3.0`.
- **Codes consommateur.** `CONFIG_ZMK_HID_CONSUMER_REPORT_USAGES_FULL=y` porte le plafond des usages à `0xFFF` (`hid.h`). Nos codes vont de `0x0500` à `0x0608`. La macro `ZMK_HID_USAGE(page, id)` vaut `((page << 16) | id)` (`dt-bindings/zmk/hid_usage_pages.h`) et la page consommateur est `HID_USAGE_CONSUMER` (0x0C).
- **Identifiants USB et Bluetooth.** VID/PID USB par défaut `0x1D50`/`0x615E`, et le Bluetooth (DIS PnP) prend les mêmes. C'est le filtre par défaut du moteur : on ne les change pas.
- **Écran.** Le widget `nice_view/widgets/status.c` affiche le **nom de la couche active** (`display-name`), ou « LAYER n » sans nom. Le tag de 3 lettres est donc le `display-name` de la couche, sans widget maison.
- **Brochage de l'écran.** Le shield `nice_view_adapter` pour `nice_nano_v2` met CS sur `&pro_micro 1` (D1 = P0.06), SCK sur P0.20 et MOSI sur P0.17, comme le pinout du PCB.
- **ZMK Studio.**
  - Il faut le snippet `studio-rpc-usb-uart` et `-DCONFIG_ZMK_STUDIO=y` dans `build.yaml`, une liaison `&studio_unlock` dans la keymap, et une **physical layout** avec `keys` (sans `chosen zmk,matrix-transform`).
  - Studio sait renommer les couches et changer les comportements des touches, macros maison comprises.
  - Il **ne sait pas** changer les liaisons des encodeurs : « low priority » dans la table des fonctions.
- **Encodeurs.** Pilote `alps,ec11` : `steps` = impulsions par tour × 4 (l'exemple de la doc met `steps = <80>` pour un EC11 à 20 impulsions). Le `triggers-per-rotation` se règle dans `sensors`.
- **Workflow.** `build-user-config.yml` accepte `config_path` et `build_matrix_path`. Il lance `west init -l <config_path>` puis `west build ... -DZMK_CONFIG=<config_path>`. Les shields placés dans `<config_path>/boards/shields/` sont trouvés.
- **Pas de compilation locale.** Pas de chaîne Zephyr ni de Docker sur la machine, et le choix d'Alan du 2026-10-29 est la compilation par GitHub Actions. **Seule la CI prouve que le firmware compile.**

## Écart assumé par rapport à la spec (§3.1)

La spec met la molette **gauche** en touches média natives (volume, et mute au clic), pour qu'elle marche sans logiciel. Mais ZMK Studio ne sait pas modifier les encodeurs. Une molette native resterait donc figée au volume pour toujours, alors qu'Alan veut des molettes configurables (2026-11-05 : « On rend configurables les molettes de toute façon »).

**Choix retenu** : sur tous les profils, les deux molettes, sens et clic, envoient des **codes action**. Le moteur leur donne leur rôle, et la config par défaut du moteur gagne « gauche = volume ±2, clic = couper ». Prix à payer : la molette gauche ne règle plus le volume quand le moteur est fermé. Le pavé numérique, lui, reste natif.

## Global Constraints

- Tout le firmware vit dans `firmware/` du dépôt NULL-PAD. Le workflow est `.github/workflows/firmware.yml` et ne se déclenche que sur `firmware/**`, sur lui-même ou à la main (`workflow_dispatch`).
- ZMK épinglé sur **`v0.3.0`** à deux endroits : `firmware/config/west.yml` (`revision: v0.3.0`) et `uses: zmkfirmware/zmk/.github/workflows/build-user-config.yml@v0.3.0`.
- Carte `nice_nano_v2` ; shields `null_pad nice_view_adapter nice_view` ; snippet `studio-rpc-usb-uart` ; `cmake-args: -DCONFIG_ZMK_STUDIO=y`.
- Nom : `CONFIG_ZMK_KEYBOARD_NAME="NULL/PAD"`. VID/PID inchangés (`0x1D50`/`0x615E`).
- Brochage (source de vérité : PROJECT.md « Pinout », broches `&pro_micro N` = Dn) :
  - **Matrice col2row**, diodes côté rangée :
    - rangées ROW0–ROW4 = D5, D6, D7, D8, D9 ;
    - colonnes COL0–COL4 = D19, D18, D15, D14, D16.
  - **Encodeur gauche (ENC1)** : A = D0, B = D4.
  - **Encodeur droit (ENC2)** : A = D21, B = D20.
  - **Encodeurs PEC11R 24/24** : `steps = <96>`, `triggers-per-rotation = <24>`, pull-ups internes.
  - **D16 = P0.10, une broche NFC** : `&uicr { nfct-pins-as-gpios; };` obligatoire.
- **Positions des touches** (= ordre de la physical layout et de la transform) :
  - 0–19 = la grille 4 × 5, rang par rang depuis le haut à gauche (`RC(r, c)`, r 0–4, c 0–3). C'est l'ordre `K00`–`K19` du moteur.
  - 20 = M1 `RC(2,4)`, 21 = M2 `RC(3,4)`, 22 = M3 `RC(4,4)`.
  - 23 = clic ENC1 `RC(0,4)`, 24 = clic ENC2 `RC(1,4)`.
- **Codes** (moteur, `engine/src/codes.rs`) :
  - action `0x0500 + (p-1)*32 + i` (p 1–8 = couche + 1) ;
  - annonce `0x0600 + p` ;
  - entrées : `K00`–`K19` = 0–19, M1–M3 = 20–22, `ENC_L_CW` 23, `ENC_L_CCW` 24, `ENC_L_PRESS` 25, `ENC_R_CW` 26, `ENC_R_CCW` 27, `ENC_R_PRESS` 28.
  - Aucune valeur écrite en dur dans la keymap : tout passe par `ACT(p, i)` et `ANN(p)`.
- 8 couches = profils 1–8, `display-name` = tag de 3 caractères `[A-Z0-9]` : `DEF`, `P02`, …, `P08`.
- Anti-rebond : `debounce-press-ms = <1>`, `debounce-release-ms = <5>` (à régler sur le vrai PCB, spec §3.1).
- Le moteur reste vert : `cargo test -p engine`, `cargo clippy -p engine --all-targets -- -D warnings`. Commandes cargo **sans** `rtk`.
- Messages de commit terminés par `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Travail sur la branche `feat/firmware`. **Pousser la branche** (pour que la CI compile) demande l'accord d'Alan, demandé une fois au début de l'exécution.

## Review Focus

1. **Décalage entre firmware et moteur** : une touche ou une molette envoie un code que le moteur décode vers une autre entrée ou un autre profil. Test : Task 1 (en-tête ↔ `codes.rs`), plus la relecture de la keymap (Task 2).
2. **La broche NFC P0.10 (COL4) reste inactive**, et M1–M3 et les clics ne répondent pas. Test : `uicr` présent (Task 2), à confirmer sur le module (Task 3, liste à la main).
3. **Le pavé numérique ne marche pas sans logiciel** (anti-objectif de la spec). Test : couche 0 en codes clavier natifs `KP_*`, relue en Task 2.
4. **Plus moyen d'éditer avec ZMK Studio** (pas de physical layout, ou pas de touche de déverrouillage). Test : la CI compile avec le snippet ; combo de déverrouillage documenté (Tasks 2 et 3).
5. **La molette gauche ne fait plus rien sans moteur**, alors que l'utilisateur s'attend au volume. C'est l'écart assumé : il est écrit dans `firmware/README.md` et dans la spec (Task 3), et le moteur règle le volume par défaut (Task 1).
