**Goal:** un firmware ZMK pour le NULL/PAD, compilé en local sous WSL (GitHub Actions possible, mais bloqué chez Alan) pour le dépôt `Telooss/NULL-PAD`.
- Le pad est un pavé numérique autonome (profil 1).
- 8 profils (couches ZMK) se choisissent par M1–M3.
- Le firmware envoie au moteur les codes « action » et « annonce de profil » qu'il attend.
- Le nice!view affiche le tag du profil.
- Tout, **molettes comprises**, reste éditable par ZMK Studio (donc par l'appli NULL/PAD, qui parlera le même protocole).

**Architecture :**
- Un shield ZMK `null_pad` (plus `nice_view_adapter` et `nice_view`) pour la carte `nice_nano_v2`. Le SuperMini est un clone du nice!nano v2.
- Config dans `firmware/` (west.yml, keymap, shield sous `boards/shields/null_pad/`), matrice de compilation dans `firmware/build.yaml`.
- Un petit **module ZMK** à nous dans `firmware/module/`, déclaré par `zephyr/module.yml` à la racine du dépôt, que le workflow charge tout seul. Il transforme chaque cran de molette en appui sur une **touche cachée**.
- `.github/workflows/firmware.yml` appelle le workflow officiel `build-user-config.yml` de ZMK, épinglé sur `v0.3.0`.
- Les codes action passent par une macro du préprocesseur, `ACT(profil, entrée)`, qui recopie la formule du moteur. Un test Rust vérifie que l'en-tête et `codes.rs` sont d'accord.
- Une **position de touche vaut l'`InputId` du moteur** (0–28).

**Tech Stack:** ZMK **v0.3.0** (Zephyr 3.5, carte `nice_nano_v2`), devicetree / Kconfig, C (module Zephyr), GitHub Actions, Rust (un test dans `engine`).

**Spec:** `docs/superpowers/specs/2026-11-05-logiciel-macropad-design.md` (§3.1 Firmware, §4 Profils). Matériel : `PROJECT.md` du dossier matériel (hors dépôt), sections « Pinout » et « Layout ». Codes : `docs/superpowers/plans/2026-11-05-moteur.md`, « Table des codes ».

## Faits vérifiés dans les sources de ZMK v0.3.0 (2026-11-06)

- **Version.** Dernière version publiée : `v0.3.0` (2025-08-01), sur Zephyr 3.5, carte `nice_nano_v2`. La branche `main` est sur Zephyr 4.1 avec d'autres noms de cartes : on reste sur `v0.3.0`.
- **Codes consommateur.**
  - `CONFIG_ZMK_HID_CONSUMER_REPORT_USAGES_FULL=y` relève le plafond des usages à `0xFFF`. Nos codes vont de `0x0500` à `0x0608`.
  - `ZMK_HID_USAGE(page, id)` = `((page << 16) | id)` (`dt-bindings/zmk/hid_usage_pages.h`).
  - La page consommateur est `HID_USAGE_CONSUMER` (0x0C).
- **Identifiants.** VID/PID USB par défaut `0x1D50`/`0x615E`, et le Bluetooth (DIS PnP) prend les mêmes. C'est le filtre par défaut du moteur : on n'y touche pas.
- **Écran.**
  - `nice_view/widgets/status.c` affiche le **nom de la couche active** (`display-name`), ou « LAYER n » quand la couche n'a pas de nom.
  - Le `nice_view_adapter` pour `nice_nano_v2` met CS sur `&pro_micro 1` (D1 = P0.06), SCK sur P0.20 et MOSI sur P0.17, comme notre PCB.
- **ZMK Studio.**
  - Il faut le snippet `studio-rpc-usb-uart`, `-DCONFIG_ZMK_STUDIO=y`, une liaison `&studio_unlock`, et une **physical layout** avec `keys` (sans `chosen zmk,matrix-transform`).
  - Studio sait changer les comportements des touches (macros maison comprises) et renommer les couches.
  - Il **ne sait pas** changer les `sensor-bindings` des encodeurs : c'est noté « low priority ». D'où les touches cachées.
- **API pour le module.**
  - `struct zmk_position_state_changed { uint8_t source; uint32_t position; bool state; int64_t timestamp; }` (`zmk/events/position_state_changed.h`).
  - Les comportements de molette implémentent `sensor_binding_accept_data` et `sensor_binding_process` (`drivers/behavior.h`). Modèles à suivre : `app/src/behaviors/behavior_sensor_rotate_common.c` et `behavior_sensor_rotate.c`.
- **Encodeurs.** Pilote `alps,ec11` : `steps` = impulsions par tour × 4 (la doc met `steps = <80>` pour un EC11 à 20 impulsions). `triggers-per-rotation` se règle dans `sensors`.
- **Workflow.**
  - `build-user-config.yml` accepte `config_path` et `build_matrix_path`.
  - Il ajoute `-DZMK_EXTRA_MODULES=<racine du dépôt>` si `zephyr/module.yml` existe à la racine.
  - Il trouve les shields placés dans `<config_path>/boards/shields/`.
- ~~Pas de compilation locale… Seule la CI prouve que le firmware compile.~~ **Périmé** (voir la note en tête) : la compilation se fait en local sous WSL avec `firmware/build-local.sh`.

## Contournement : les molettes en touches cachées (décidé avec Alan le 2026-11-06)

ZMK Studio ne sait pas éditer les molettes. Le firmware ajoute donc **4 positions de touche qui n'existent pas physiquement** : molette gauche horaire et anti-horaire, molette droite horaire et anti-horaire.

- Les quatre positions sont dans la physical layout, donc visibles et éditables dans Studio. Elles sont aussi dans la transform, sur une 6ᵉ rangée que le scan ne lit jamais.
- Le comportement de molette du module, `&np_enc`, émet pour chaque cran un appui puis un relâchement sur la position cachée du sens tourné. Couches, combos et Studio s'appliquent comme pour une vraie touche.
- **Défauts.**
  - **Molette gauche** : volume natif (`C_VOL_UP`, `C_VOL_DN`), clic = `C_MUTE`, sur toutes les couches. Elle marche sans logiciel, comme le veut la spec §3.1.
  - **Molette droite** : codes action (micro, réglé par le moteur).
  - Les deux restent modifiables, par profil, dans Studio comme dans l'appli.

## Global Constraints

- Tout le firmware vit dans `firmware/` du dépôt NULL-PAD, plus `zephyr/module.yml` à la racine. Le workflow `.github/workflows/firmware.yml` ne se déclenche que sur `firmware/**`, `zephyr/**`, lui-même, ou à la main (`workflow_dispatch`).
- ZMK épinglé sur **`v0.3.0`** à deux endroits : `firmware/west.yml` (`revision: v0.3.0`) et `uses: zmkfirmware/zmk/.github/workflows/build-user-config.yml@v0.3.0`.
- Carte `nice_nano_v2` ; shields `null_pad nice_view_adapter nice_view` ; snippet `studio-rpc-usb-uart` ; `cmake-args: -DCONFIG_ZMK_STUDIO=y`.
- Nom : `CONFIG_ZMK_KEYBOARD_NAME="NULL/PAD"`. VID/PID inchangés (`0x1D50`/`0x615E`).
- **Brochage** (source de vérité : PROJECT.md « Pinout » ; `&pro_micro N` = broche Dn).
  - Matrice **col2row**, diodes côté rangée :
    - rangées ROW0–ROW4 = D5, D6, D7, D8, D9 ;
    - colonnes COL0–COL4 = D19, D18, D15, D14, D16.
  - Encodeur gauche (ENC1) : A = D0, B = D4.
  - Encodeur droit (ENC2) : A = D21, B = D20.
  - PEC11R 24/24 : `steps = <96>`, `triggers-per-rotation = <24>`, pull-ups internes.
  - D16 = P0.10 est une broche NFC : `&uicr { nfct-pins-as-gpios; };` est obligatoire.
- **Positions des touches = `InputId` du moteur.** C'est l'ordre de la physical layout et de la transform.
  - 0–19 : la grille 4 × 5, rang par rang depuis le haut à gauche, `RC(r, c)` avec r 0–4 et c 0–3.
  - 20, 21, 22 : M1 `RC(2,4)`, M2 `RC(3,4)`, M3 `RC(4,4)`.
  - 23 : ENC_L_CW, caché, `RC(5,0)`.
  - 24 : ENC_L_CCW, caché, `RC(5,1)`.
  - 25 : clic ENC1 `RC(0,4)`.
  - 26 : ENC_R_CW, caché, `RC(5,2)`.
  - 27 : ENC_R_CCW, caché, `RC(5,3)`.
  - 28 : clic ENC2 `RC(1,4)`.
  - La transform a 6 rangées × 5 colonnes. Le kscan n'en a que 5 × 5, donc la rangée 5 n'est jamais lue.
- **Codes** (moteur, `engine/src/codes.rs`) :
  - action `0x0500 + (p-1)*32 + i`, avec p 1–8 = couche + 1 ;
  - annonce `0x0600 + p`.
  - Aucune valeur en dur dans la keymap : tout passe par `ACT(p, i)` et `ANN(p)`.
- **Couches.** 8 couches = profils 1–8. `display-name` = tag de 3 caractères `[A-Z0-9]` : `DEF`, `P02`, …, `P08`.
- **Anti-rebond** : `debounce-press-ms = <1>`, `debounce-release-ms = <5>`, à régler sur le vrai PCB (spec §3.1).
- Le moteur reste vert : `cargo test -p engine` et `cargo clippy -p engine --all-targets -- -D warnings`. Commandes cargo **sans** `rtk`.

## Review Focus

1. **Décalage firmware ↔ moteur** : un code décodé vers une autre entrée ou un autre profil. Tests : Task 1 (en-tête ↔ `codes.rs`) et relecture de la keymap (Task 3).
2. **Un cran de molette qui donne zéro ou deux appuis, ou une touche cachée qui reste enfoncée** : appui et relâchement par cran, rien quand le cran est incomplet. Test : relecture du module (Task 2) et liste à tester (Task 4).
3. **Broche NFC P0.10 (COL4) inactive** : M1–M3 et les clics ne répondent plus. Test : `uicr` présent (Task 3), à confirmer sur le module (Task 4).
4. **Pavé numérique qui ne marche pas sans logiciel** (anti-objectif de la spec). Test : couche 0 en `KP_*` natifs et molette gauche native, relues en Task 3.
5. **ZMK Studio inutilisable** (pas de physical layout, touches cachées absentes, pas de déverrouillage). Test : la CI compile avec le snippet, et la combo de déverrouillage est documentée (Tasks 3 et 4).

  - **COL4 / P0.10** : M1–M3 et les deux clics répondent (broche NFC).
  - **Pavé** : en profil 1, logiciel fermé, chaque touche tape le bon caractère ; la molette gauche règle le volume.
  - **Codes** : avec le moteur (logs), une touche « M » et la molette droite produisent l'entrée et le profil attendus.
  - **Crans** : un cran = un appui ; le sens horaire est bien `CW` ; sinon corriger `steps` / `triggers-per-rotation` ou inverser A/B.
  - **Écran** : affiche `DEF`, puis `P02` / `P03` après M2 / M3.
  - **Bluetooth** : le moteur reconnaît le pad (VID/PID `0x1D50`/`0x615E`).
  - **Studio** : se connecte en USB après M1 + M3 ; une touche cachée de molette modifiée dans Studio change bien la molette.
  - **Anti-rebond** : pas de double frappe avec 1 ms à l'appui ; sinon remonter `debounce-press-ms`.
