# Moteur (Rust) — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** un programme Windows en arrière-plan qui reçoit les codes « action » du macropad et exécute l'action configurée pour ce profil et cette touche, en moins de 1 ms.

**Architecture:** le macropad envoie, pour chaque touche « action », un code HID **Consumer** (page 0x0C) que Windows n'utilise pas. Le moteur les lit via **Raw Input** (fenêtre message-only, `RIDEV_INPUTSINK`), transforme les rapports en appuis/relâchements, passe par une machine d'états (appui / appui long / double appui), cherche la liaison dans la config JSON et exécute l'action sur un thread de travail. Tout ce qui est logique pure est testé sans matériel ; un mode `--simulate` injecte des codes depuis le clavier pour les essais à la main.

**Tech Stack:** Rust stable (1.97 présent sur la machine), crates `windows` (Win32 : Raw Input, SendInput, ShellExecute, Core Audio), `serde` + `serde_json`, `arc-swap`, `notify` (rechargement à chaud), `tray-icon` + `winit` ou boucle Win32 (icône), `winreg` (démarrage avec Windows), `dirs`, `tracing` + `tracing-appender`.

**Spec:** `docs/superpowers/specs/2026-11-05-logiciel-macropad-design.md`

## Écart assumé par rapport à la spec

La spec (§3.1) prévoyait F13–F24 combinés avec Ctrl/Maj/Alt, captés par un hook clavier. Problème découvert en planifiant : le macropad envoie le modificateur et la touche dans le même rapport, Windows délivre d'abord « Ctrl enfoncé ». Le hook ne peut pas le bloquer sans retarder les vrais Ctrl. Les jeux verraient donc un Ctrl fantôme (accroupi), et un Alt fantôme ouvre le menu des applis.

**Choix retenu :** des codes HID Consumer réservés, lus en Raw Input. Windows ne les associe à aucune touche : aucune appli ne les voit, rien à bloquer, pas de hook clavier, et on sait de quel appareil ils viennent. Le code encode **le profil et la touche**, donc le moteur ne peut jamais se tromper de profil.
**À vérifier sur le vrai macropad (plan firmware) :** que ZMK envoie bien ces usages (`CONFIG_ZMK_HID_CONSUMER_REPORT_USAGES_FULL=y`, `ZMK_HID_USAGE(HID_USAGE_CONSUMER, …)`) et que Windows les ignore. Repli si ça échoue : F13–F24 sans modificateur via hook bas niveau (12 codes, donc moins de touches action par profil).

## Global Constraints

- Windows 11 uniquement. Un seul macropad.
- Latence : < 1 ms entre la réception du rapport et le lancement de l'action (hors durée de l'action). Une action à appui simple part **à l'appui**, pas au relâchement.
- Le moteur n'attend jamais l'interface ; l'interface peut être fermée.
- Une config invalide ne remplace jamais la dernière config valide (pas de perte).
- Profils : 1 à 8. Tag : exactement 3 caractères `[A-Z0-9]`.
- Dossier du code : `logiciel/` (dépôt git propre), crate `logiciel/engine`. Config : `%APPDATA%\macropad\config.json` (nom de dossier dans **une seule** constante `APP_DIR`, le nom définitif du logiciel n'est pas choisi).
- Commandes cargo préfixées par `rtk` (préférence d'Alan).
- Messages de commit terminés par `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Table des codes (source de vérité, réutilisée par le plan firmware)

- Entrées (`InputId`, 0–28) : touches `K00`–`K19` = grille 5 rangées × 4 colonnes, rang par rang depuis le haut à gauche (`index = rangée*4 + colonne`) ; `K20`–`K22` = M1, M2, M3 ; `ENC_L_CW`=23, `ENC_L_CCW`=24, `ENC_L_PRESS`=25, `ENC_R_CW`=26, `ENC_R_CCW`=27, `ENC_R_PRESS`=28.
- Code action : `usage = 0x0500 + (profil-1)*32 + input` (profil 1–8).
- Code annonce de profil (envoyé par les touches de profil, sert à l'interface) : `usage = 0x0600 + profil`.

## Review Focus

1. **Config à moitié écrite pendant le rechargement** (l'interface sauvegarde pendant que le moteur lit) → le moteur garde l'ancienne config, journalise, ne plante pas. Test : Task 9.
2. **Plusieurs touches à la fois** (rapport avec plusieurs usages, relâchements dans le désordre) → chaque touche déclenche et se relâche correctement. Test : Task 2.
3. **Macro longue en cours** (délais de plusieurs secondes) → les autres touches restent instantanées. Test : Task 7.
4. **Macropad débranché ou Bluetooth coupé pendant un appui** → aucune touche « coincée », aucun appui long fantôme. Test : Task 3 (`reset`) + Task 8 (appel sur `GIDC_REMOVAL`).
5. **Code inconnu, profil absent de la config, touche sans liaison, programme introuvable** → ignoré ou journalisé, jamais de plantage. Tests : Tasks 1, 6, 7.

  - `pub struct Timing { pub hold_ms: u64, pub double_ms: u64 }` — défauts **300** et **250** (choix de Claude).
  - `pub struct Fire { pub profile: u8, pub input: InputId, pub trigger: Trigger }`
  - `pub struct Triggers` : `pub fn new(timing: Timing) -> Self` ; `pub fn down(&mut self, profile: u8, input: InputId, wants: Wants, now: Instant) -> Vec<Fire>` ; `pub fn up(&mut self, profile: u8, input: InputId, now: Instant) -> Vec<Fire>` ; `pub fn tick(&mut self, now: Instant) -> Vec<Fire>` ; `pub fn next_deadline(&self) -> Option<Instant>` ; `pub fn reset(&mut self)`.
  - `pub struct Wants { pub hold: bool, pub double: bool }` : quelles liaisons existent pour cette touche (fourni par la config).

Règles (l'implémenteur ne peut pas les deviner) :
- Rotation de molette (`is_rotation`) ou `Wants{hold:false,double:false}` → `Press` **immédiatement à l'appui**.
- `hold` seul → `Hold` si tenu ≥ hold_ms (via `tick`), sinon `Press` au relâchement.
- `double` seul → second appui dans double_ms → `DoubleTap` ; sinon `Press` à l'expiration (via `tick`).
- `hold` + `double` → combinaison des deux règles, `Hold` prioritaire.
- `reset` oublie tout état en cours sans rien déclencher.
